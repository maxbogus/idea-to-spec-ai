# Eval промптов — отчёты и находки

> Автоматическая проверка, что промпты работают так, как описано в
> `handout-index.md` и `prompts/rules.md`. Обвязка: `eval/`, `scripts/*.py`,
> `tests/`. Реальный прогон — на локальной модели через Ollama.

## Как запускать

```bash
make eval-setup   # один раз: uv sync + npm install
make eval-mock    # детерминированный replay без LLM (зелёный в CI)
make eval         # реальный прогон qwen2.5:7b, отчёт в docs/evaluation/
make test-eval    # pytest-контракты (mock + slow)
```

- Отчёт: `docs/evaluation/eval-qwen2.5-7b.json`.
- Сводка: `scripts/summarize_eval.py`.
- Провалы модели фиксируются как `xfail(strict=True)` в
  `tests/test_eval_contract.py` (`KNOWN_MODEL_FAILURES`).

## Набор кейсов

`eval/cases/roles.jsonl` — 20 кейсов (полный пайплайн):

| Сценарий | Что проверяет |
|---|---|
| `ORCH` | оркестратор: формат JSON, режимы auto/chat/hybrid, три блока вопроса |
| `PM` | product manager: измеримая метрика с базой, варианты с возражениями |
| `BA` | business analyst: персоны, JTBD, BR/AC, границы роли |
| `SA` | system analyst: use cases, FR/NFR, трассировка FR→BR, границы роли |
| `ARCH` | architect: компоненты, интеграции, ADR, наблюдаемость, контроли рисков |
| `DESIGN` | designer: user flow, экраны, трения, доступность, локализация |
| `PROJ` | project manager: задачи, риски с владельцем, roadmap, точки пересмотра |
| `FC` | fact-check: три статуса основания, понижение без источника, причина отказа |
| `DISC` | дисциплина «факт / гипотеза / прогноз» и «решение ≠ потребность» |
| `NEG` | негативные: пустая идея, пропуск гейтов |

## Результат прогона (qwen2.5:7b)

**18/20 (90%)**, нарушений границ ролей — 0, нарушений режима — 1 (ORCH-02).
Два known-failure зафиксированы в `KNOWN_MODEL_FAILURES` (ORCH-02, NEG-01).

## Что поймали прогоны (и что исправлено)

Первый прогон (MVP) дал 4/12 и выявил реальные расхождения промптов:

| Находка | Исправление |
|---|---|
| Формат PM не содержал `variants`/`assumptions`, хотя `methods/variants.md` и `prompts/rules.md` их требуют | поля добавлены в `prompts/roles/product-manager.md` |
| Оркестратор не задавал формат трёх блоков вопроса — модель выдавала объект с английскими ключами `question`/`why` | в `prompts/orchestrator.md` явно задан массив строк с метками «Вопрос: / Зачем я это спрашиваю: / Термины:» |
| Оркестратор не знал правила «пустая идея → попроси строку» (оно было только в `start.md`) | правило добавлено в `prompts/orchestrator.md` |
| BA мог выдать выдуманный источник | добавлено: при отсутствии источника — `source: "допущение"` |

После исправлений — 9/12.

### Этап 2: Architect, Designer, Project Manager, fact-check

После добавления четырёх ролей (20 кейсов) прогон дал 15/20 и выявил ещё три
проблемы:

| Находка | Исправление |
|---|---|
| Формат fact-check не задавал вывод — контракт был непроверяем | добавлен раздел «Формат вывода» (`status` / `source` / `reason`) в `subagents/fact-check.md` |
| Модель уходила в китайский язык, хотя поля формально на месте | в промпт добавлено «Отвечай на русском языке», в assert — проверка кириллицы |
| FC-02 требовал русское «причин», а формат использует ключ `reason` | контракт выровнен со структурой (`reason`) |

После исправлений — 18/20.

## Оставшиеся known-failures

| Кейс | Причина | Класс |
|---|---|---|
| `ORCH-02-chat-three-block-questions` | в режиме chat модель задаёт 4 вопроса вместо ≤ 3; число плавает между прогонами | свойство модели |
| `NEG-01-empty-idea` | на пустой идее модель всё равно начинает прогон и пишет артефакты | пробел модели |

## Как добавить кейс

1. Добавить строку в `eval/cases/roles.jsonl` (поля: `id`, `role`, `scenario`,
   `kind`, `title`, `mode`, `input`, `expected_fields`, `must_contain`,
   `must_not_contain`, `mode_check`, `notes`).
2. Добавить «идеальный» ответ в `scripts/mock_provider.py` (по префиксу `id`).
3. Обновить `docs/evaluation/README.md` и, при необходимости,
   `tests/test_eval_contract.py` (ожидаемый размер набора).

## Как обновлять `KNOWN_MODEL_FAILURES`

`xfail(strict=True)` превращает внезапный проход в ошибку теста. Если модель
стала проходить кейс — уберите его из `KNOWN_MODEL_FAILURES`. Если новый кейс
провалился и это свойство модели, а не контракта — добавьте его в список с
комментарием-причиной.
